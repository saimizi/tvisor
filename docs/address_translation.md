# AArch64 address translation for tvisor

## 1. Purpose

This document explains the address-translation regimes relevant to tvisor on
the Raspberry Pi 4. It distinguishes:

- tvisor's own EL2 stage-1 translation;
- a guest's EL1/EL0 stage-1 translation;
- tvisor-controlled stage-2 translation for that guest.

The current U-Boot handoff diagnostic only observes inherited register values.
It does not install translation tables or change the MMU configuration.

## 2. Address types

Arm virtualization uses three address names:

| Name | Meaning |
| --- | --- |
| VA | Virtual Address generated by software. |
| IPA | Intermediate Physical Address produced by guest stage 1. It is the address the guest believes is physical. |
| PA | Physical Address used to access real RAM or a peripheral. |

Without active stage 2, an EL1/EL0 stage-1 output is used as a PA. With stage 2
enabled, the same output is an IPA that must be translated again.

## 3. Independent translation regimes

AArch64 has separate stage-1 translation regimes rather than one system-wide
set of page tables:

```text
EL1/EL0 software -> EL1 stage 1 -> IPA or PA
EL2 software     -> EL2 stage 1 -> PA
EL3 software     -> EL3 stage 1 -> PA
```

EL0 has no `SCTLR_EL0`, `TCR_EL0`, or `TTBR_EL0`. EL0 uses the EL1-controlled
translation regime. EL2 and EL3 each have their own independent regime.

Stage 2 applies to accesses made by the guest EL1/EL0 regime. It does not
normally translate tvisor's own EL2 accesses.

## 4. Stage-1 translation

Stage 1 is the normal operating-system translation from a software virtual
address to an address representing memory:

```text
VA -> stage-1 page tables -> output address
```

For a guest, the output becomes an IPA when stage 2 is active. For tvisor at
EL2, the output is a PA.

### 4.1 tvisor's EL2 stage 1

```text
tvisor VA
    |
    | SCTLR_EL2.M, TCR_EL2, TTBR0_EL2, MAIR_EL2
    v
PA
```

The main registers are:

| Register | Role |
| --- | --- |
| `SCTLR_EL2` | `M` enables EL2 stage 1. It also controls EL2 caches, alignment checks, endianness, and related behavior. |
| `TCR_EL2` | Selects virtual-address size, granule, table-walk cacheability/shareability, and supported output address size. |
| `TTBR0_EL2` | Points to the root of tvisor's EL2 stage-1 tables. |
| `MAIR_EL2` | Defines the Normal and Device memory types referenced by stage-1 descriptors. |

If `SCTLR_EL2.M == 0`, tvisor does not use EL2 stage-1 address translation.
The other EL2 translation registers can still contain nonzero values, but
they are inactive or stale for ordinary EL2 accesses.

### 4.2 guest EL1/EL0 stage 1

```text
guest VA
    |
    | SCTLR_EL1, TCR_EL1, TTBR0_EL1/TTBR1_EL1, MAIR_EL1
    v
IPA when stage 2 is enabled; otherwise PA
```

The guest OS normally owns these registers and its stage-1 page tables. This
allows it to manage kernel and application virtual address spaces just as it
would on a non-virtualized machine.

## 5. Stage-2 translation

Stage 2 lets tvisor translate and restrict the guest's view of physical
memory:

```text
guest VA
    |
    | guest stage 1
    v
guest IPA
    |
    | tvisor stage 2
    v
real PA
```

For example:

```text
Guest VA  0x0000_0000_0000_4000
    -> stage 1
Guest IPA 0x0000_0000_8000_4000
    -> stage 2
Real PA   0x0000_0000_4100_4000
```

The guest can manage the VA-to-IPA mapping, but only tvisor owns the IPA-to-PA
mapping. Stage 2 therefore lets tvisor:

- isolate guest RAM from tvisor and other guests;
- relocate guest memory without changing the guest's page tables;
- make regions read-only or execute-never;
- expose only selected MMIO devices;
- generate a stage-2 fault when the guest accesses an unmapped or forbidden
  IPA.

### 5.1 Stage-2 registers

| Register | Role |
| --- | --- |
| `HCR_EL2.VM` | Enables stage-2 translation for the applicable Non-secure EL1/EL0 regime. |
| `VTCR_EL2` | Defines the IPA size, starting lookup level, granule, table-walk attributes, and PA size for stage 2. |
| `VTTBR_EL2` | Holds the stage-2 root-table address and the VMID identifying the guest. |

`HCR_EL2.VM` is independent of `SCTLR_EL2.M`. A typical hypervisor can have
both set:

```text
SCTLR_EL2.M = 1  tvisor uses EL2 stage 1
HCR_EL2.VM  = 1  guest accesses use stage 2
```

It is also architecturally possible for tvisor to use physical addresses with
`SCTLR_EL2.M == 0` while protecting a guest with `HCR_EL2.VM == 1`.

## 6. Common configurations

| EL2 stage 1 | Guest stage 1 | Stage 2 | Result |
| --- | --- | --- | --- |
| Off | Off | Off | tvisor and guest use addresses directly as PAs. No guest memory isolation is provided by translation. |
| On | Off | Off | tvisor has a virtual address space; the guest still uses PAs directly. |
| On or off | On | Off | guest VA translates directly to PA. The guest controls what real memory its tables can address. |
| On or off | Off | On | the guest address is used as an IPA and stage 2 translates it to PA. This can protect a guest before it enables its own MMU. |
| On or off | On | On | guest VA translates to IPA and then PA. This is the normal virtual-machine arrangement. |

For an isolated guest, tvisor normally needs stage 2 enabled. Guest stage 1 is
not a substitute for stage 2 because the guest controls its own stage-1 tables.

## 7. Permissions and memory attributes

Both stages can specify access permissions and attributes. An access must be
permitted by both stages. A guest cannot use a permissive stage-1 mapping to
override a read-only, execute-never, or unmapped stage-2 entry.

The architecture combines stage-1 and stage-2 memory attributes to obtain the
effective access type. Tvisor must map RAM as suitable Normal memory and MMIO
as Device memory. Incorrect attributes can cause broken ordering, stale data,
or unsafe speculative accesses to devices.

Stage-1 descriptors select memory types defined by `MAIR_EL1` or `MAIR_EL2`.
Stage-2 descriptors encode their stage-2 memory attributes according to the
stage-2 translation format; they do not use a separate `MAIR` register.

## 8. TLB tags and VMIDs

The Translation Lookaside Buffer caches translations. Guest stage-1 entries
can use ASIDs to distinguish address spaces. Stage-2 translations use the VMID
in `VTTBR_EL2` to distinguish guests, allowing entries from multiple guests to
coexist in the TLB.

A VMID is not a permission mechanism by itself. Tvisor must allocate and reuse
VMIDs carefully and perform the architecturally required stage-2 TLB
invalidation when mappings change or a VMID is reused.

## 9. Fault ownership

- A guest stage-1 translation or permission fault belongs to the guest's
  virtual-memory regime and is normally handled by the guest at EL1.
- A stage-2 translation or permission fault is caused by tvisor's IPA-to-PA
  policy and traps to EL2 for tvisor to handle.
- A fault in tvisor's own EL2 stage-1 regime is an EL2 fault and requires a
  valid EL2 vector table and handler.

Before enabling stage 2 and entering a guest, tvisor therefore needs a valid
`VBAR_EL2` and enough exception handling to decode and report stage-2 faults.

## 10. Safe future initialization order

The current diagnostic must remain read-only. A later guest initialization
path should broadly:

1. Discover supported granules, PA size, VMID width, and virtualization
   features from the architectural ID registers.
2. Reserve aligned memory for stage-2 tables and clear it.
3. Build explicit IPA-to-PA mappings with deliberate permissions and memory
   attributes.
4. Install a private EL2 stack, `VBAR_EL2`, and exception handlers.
5. Program `VTCR_EL2` for the selected table format.
6. Program `VTTBR_EL2` with the root address and guest VMID.
7. Perform required cache maintenance, barriers, and stage-2 TLB invalidation.
8. Set the intended `HCR_EL2` fields, including `VM` and the EL1 execution
   state in `RW`.
9. Execute the required synchronization before entering the guest with
   `ERET`.

Do not set `HCR_EL2.VM` before valid stage-2 tables and EL2 exception handling
exist. Otherwise, the guest's first instruction fetch or data access can fault
immediately with no safe recovery path.

## 11. Current Raspberry Pi 4 observation

The observed U-Boot handoff currently includes:

```text
SCTLR_EL2.M = true
HCR_EL2.VM  = false
```

Therefore, U-Boot has enabled EL2 stage-1 translation for the environment in
which tvisor runs, but guest stage-2 translation is not active. Any inherited
`VTCR_EL2` and `VTTBR_EL2` values must be treated as inactive or stale until
tvisor deliberately constructs its own guest environment.
